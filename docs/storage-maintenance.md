# 第 2 版知识库的存储维护

每个知识库使用 `.ultrakb/kb.sqlite` 作为统一业务主库，`.ultrakb/blobs/`
保存按内容摘要寻址的不可变原件、正文、图片和恢复成果。资料、处理单元、索引、
知识修订、会话、任务及模型用量通过各自身份关联。相同字节共享内容，不合并来源身份。

只支持按 `ultrakb.context-kb` 第 2 版创建的知识库。旧格式和不支持的 SQLite
运行环境会在建表、恢复、写入及模型发送前被拒绝。请保留旧库，在新目录创建库后
显式导入需要的原件；重命名状态目录不能完成格式转换。

## 阅读、发布和工作副本

已提交的知识正文和输入清单独立于 `wiki/`。一次读取绑定完整的公开版本；
HTTP 返回的 `publication_id` 可用于固定后续正文、图片和来源请求。
模型处理期间仍可阅读旧的完整版本。发布成功后，工作副本待同步不影响已提交知识可读。

首次编译失败的资料可以显式选择保留的处理单元修订阅读，详见[来源阅读](source-reading.md)。
普通知识阅读不会采用未发布的输入，也不会暗中调用模型、建立导航或修复主库。

应用内编辑检查编辑基线，知识版本变化时会返回冲突。外部编辑器应先通过桌面的
Wiki 维护操作暂停同步，再修改 `wiki/`。暂停状态跨重启保留，后台发布继续写主库，
不会替换暂停中的文件。完成后显式接纳或放弃差异，再恢复同步；接纳时会重新检查基线。
对绕过暂停协议的直接文件写入，系统不能保证文件检查与替换之间绝对没有竞争。

## 诊断和显式修复

桌面菜单可在无法打开知识库时进行诊断，读取已提交页面和恢复状态。
诊断不会以 `raw/` 或当前 Wiki 内容覆盖主库。设置文件写入中断需通过显式修复恢复；
无法识别的恢复材料会继续保留并报告。

以下维护操作不需要模型凭据，也不发送新请求：

```bash
ultrakb --kb-dir /path/to/kb storage repair-receipts
ultrakb --kb-dir /path/to/kb storage repair-navigation
ultrakb --kb-dir /path/to/kb storage audit-usage
```

`repair-receipts` 有界接纳已保留的模型响应和用量。无法核验的回执继续待修复，
不会被当作未发送后自动重试。编译、索引和会话已经接受的计算成果独立于知识发布保留。

`repair-navigation` 从当前公开版本的已提交输入重建确定性知识导航，返回所修复的
公开身份和知识修订。它不重编译资料，不改变知识正文，也不消耗模型预算。
桌面存储维护面板的“修复知识导航”和认证 HTTP
`POST /api/v1/storage/repair-navigation` 调用同一共享用例。

HTTP 维护写入需携带 `kb`、`kb_id` 和 `generation`。CLI 也可通过
`--kb-id` 和 `--generation` 固定预览时的库身份。知识库被替换或恢复后，旧身份会被拒绝。

## 预览和清理

```bash
ultrakb --kb-dir /path/to/kb storage preview
ultrakb --kb-dir /path/to/kb storage candidates
ultrakb --kb-dir /path/to/kb storage retire-roots --max-items 128
ultrakb --kb-dir /path/to/kb storage collect --max-items 128 --max-bytes 67108864
```

预览显示受保护内容、可退役恢复引用、孤立内容和批次上限。预览不授权删除；
每次执行都会重新核对引用。清理分为显式放弃已审阅候选、退役无用恢复引用、回收孤立内容。
仍有引用的原件、历史、会话检查点和待确认回执受保护，不会因任务列表整理而消失。
有更多候选时，可继续下一批。

真实读取、回执存储和备份访问期间，GC 需要的排他租约可能返回 `busy`，本批不删除。
只使用已捕获输入的模型等待不会持续占用回收租约。被取消的工作仍会等待存储访问收尾，
随后再结束执行。

阶段观测默认保留 90 天，诊断载荷采用 30 天和 512 MiB 的整理目标。
`archive-observations` 和 `archive-diagnostics` 只显式处理一批符合条件的明细；
正在使用或支撑恢复的记录继续保护。核心请求、实际用量和接受成果不随可选明细归档删除。
归档结果保留覆盖声明，不能将汇总当作完整逐项详情。

## 备份和恢复

```bash
ultrakb --kb-dir /path/to/kb storage backup --output /path/to/new-backup
ultrakb storage restore /path/to/new-backup --output /path/to/new-library
```

目标必须是新的目录。备份使用 SQLite 在线快照，并在保护所需内容的期间复制和校验
快照引用的 Blob。回执分别说明已提交数据库、引用内容、本库设置、继承设置、暂停编辑差异
和待确认回执的覆盖情况；库外设置不因备份存在就变成自包含配置。

恢复校验备份后在新目录建立新的运行代次；旧任务、worker 和 UI 回调不能写入恢复后的库。
外部原件删除后仍可通过托管原件阅读和重新处理。产物的已提交正文仍可阅读和导出，
工作副本的同步确认在新目录重新建立。恢复已接受的生成计划会创建新的执行身份，
沿用原始知识输入、已付费成果和累计预算，不能借恢复重置费用限制。

活跃库的 `kb.sqlite`、WAL 和 SHM 必须一起保留。不要直接复制单个主数据库文件作为备份，
也不要手工删除协调文件。协调文件丢失时普通打开会拒绝，应从已验证的备份恢复到新目录。

CLI、桌面存储维护面板和 `/api/v1/storage` 使用相同的共享用例、身份检查及统计口径。
任务详情通过 `ultrakb tasks`、桌面任务页及 HTTP 任务接口有界加载，展示本次执行与累计用量。
