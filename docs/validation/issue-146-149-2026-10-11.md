## 实现与工程验证

摘要调用显式声明 JSON 协议，严格检查段标识、重复、缺段、空正文及语法；不再把缺尾 JSON 补齐后发布，也不降级接受 Markdown。正常每批一次生成，异常仅有限修复。

原生读取持续推进真实 continuation，取消整个必要更新的 24,000 字符总证据限制；按完整请求容量划分原文与旧页编辑块。同一基页的正文、简介和类型提案共同合并；不相交编辑组合，冲突有限处理，保留人工修改冲突和旧成功结果。

结果检查点保存在发布回滚范围之外，关联现有任务、来源和生成条件。成功摘要、提案、已解决冲突及已消耗修复机会可恢复；剩余工作准入不重复计算成功批次，调用消耗不清零。

问答沿用共享 Agent 循环，在会话准备和工具推进前保留最终发送。软停止在原执行器中禁用工具生成收尾；硬预算、截止、取消、容量失败不再额外发送，也不把工具旁白保存为成功答案。检索自动内容额度耗尽仍保留可执行原生阅读位置。

评审修复了两项具体问题：会话历史索引可能先消耗最后一次发送；旧页分块曾把完整原文误当局部范围，触发多余元数据冲突。两个 HTTP/SDK 回归均通过。原文窗口与图片的批次投影职责另收拢到 `PageOriginalContext`。

安装续办又发现一个本地性能问题：容量细分会先构造全部后续窗口，再发现第一个窗口已不能容纳。真实读器的离线回归在 34,200 字符上投影了 2964 个窗口，耗时 19.4383 秒；最小 1710 字符输入也重复投影 155 次。无网络、无分词仍可复现，不能归因于模型延迟。改为逐窗口读取、校验后暴露，并在首次容量失败时停止该次细分后，同一大用例为 10 个窗口、0.1771 秒，仍返回容量不足且零模型发送。相关 34 项测试通过，最初失败的 CPU 时间回归保留。这只证明预处理的改进，不证明原本不可容纳的内容现在可以容纳。

另一个代表性离线检查使用实际安装窗口、旧页和本地分词器，但简化任务提示，没有模型发送或页面发布。首窗口约 106 万输入 tokens，超过本次容量；旧页有 28 个编辑块。惰性读取版本在 45 秒诊断边界内作了 267 次容量检查，43.871 秒用于分词，尚未返回。加入首组早筛后，44.909 秒返回明确容量不足，268 次检查中有 157 个不同请求；最终全部组合测量仍占主要成本。该单次边界观察不构成稳定提速比例，不能据此证明安装文档已成功编译，也不能以删除图片或放宽容量换取通过。
