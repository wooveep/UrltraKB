## 3. 已确认的业务边界：跨资料系列共享同版本知识视图

Q27 已决定资料系列按“产品/主题＋用途”识别，用于资料沿革与版本关系提示；Q31 补齐知识聚合边界，系列不作为同产品同适用版本知识的隔离边界。

**Q31 已确认，用户回复“共享”**：WinStack V9.4 安装手册、运维手册是两个系列，共同构建 WinStack V9.4 知识视图，各自保留来源和修订；V9.3 使用另一个视图。同版本继续沿用 PDF 编译器原有的跨资料概念/实体整合方式，查询可同时使用两份手册的实际依据。

实施以已确认的产品身份和完整适用版本范围解析共享视图，不将 `family_id`、资料用途或资料自身修订标识加入隔离键。仍遵守以下边界：

- 不同产品只有版本号相同，不能合并；视图身份不是版本标签或 slug。
- 未标注版本不等于任意版本，也不默认等于同产品另一份未标注资料的版本。首次仍正常编译到依据范围明确的未知版本视图。
- 有依据的适用版本范围按完整范围保存，不因范围相交就自动合并；明确适用多个版本的来源保留其真实范围，不复制一个虚构的单版本标签。
- 系列默认版本是独立的选择关系，导入不修改它；跨系列查询若得到不同版本范围，分别回答，不偷偷选择统一版本。
- 为未知来源补标签是元数据修订。只有视图内全部依据均可确定映射时才能重关联；若与目标视图同名页面冲突或已有混合依据，保留原结果并显式编译合并，不能仅改目录名。

## 4. 最小文件记录契约

复用受保护文件存储与 mutation，不增加新的应用数据库。PageIndex 已有数据库继续负责索引，不承担来源业务主键。文件名和内部目录只是建议；共同存储模块拥有路径，业务代码不拼路径。

| 记录 | 最少职责/字段 |
| --- | --- |
| Source | 稳定 `source_id`、原始身份、所属系列、接入目标代次、删除/退休状态；hash 不是 ID |
| SourceRevision | `source_revision_id`、所属 Source、原件及资产清单、实际字节指纹、保存时间；冻结后不修改正文 |
| 版本注解修订 | 所属来源修订、适用对象/版本范围、资料修订标识、字段出处、用户修正及前一注解；不重写原件 |
| ImportUnit | 所属 Source、稳定 `unit_id`、正文或 sheet 的身份映射；不是 runtime 数组下标 |
| UnitRevision | 所属单元与来源修订、PDF/Markdown、规范化内容及 source map、处理指纹、分类/执行方式、索引和资产引用 |
| KnowledgeView | 稳定 `view_id`、明确适用范围/未知范围；head 保存当前知识修订、有效输入修订、代次和待刷新原因 |
| KnowledgeRevision | 不可变 `knowledge_revision_id`、基于哪一知识修订、实际输入/上下文修订、输出页面清单、页依赖、生成正文基线和创建原因 |
| 单元发布状态 | 按 `(unit_id, view_id)` 记录目标修订、已成功修订及本次失败/等待信息；不存在一个能代表全部版本的全局 active sheet |
| 待确认建议 | `proposal_id`、候选正文及资产引用、原输入/知识基线、差异与冲突原因；等待人工确认期间持久保留，不是临时 staging |
| 资产引用 | 从来源修订、单元修订、知识修订、持久意图和待确认建议引用实际原件/图片/索引；反向索引是可重建派生数据 |

记录带独立 `schema_version`；ID 用稳定、不带业务含义的标识，不用可改标题或版本标签作路径。一次失败重试沿用该意图对应的修订 ID；真正输入/处理策略改变产生新修订。重编译同一 UnitRevision 可以生成新 KnowledgeRevision，无需伪造新原件。

建议布局：

```text
KB/
  wiki/                                  # 原有 Wiki，作为 legacy 读取入口
  .openkb/
    catalog/                             # 来源、单元、注解、默认选择、状态记录
    artifacts/<content-id>/               # 共享字节，仅由引用管理回收
    knowledge/<view-id>/
      head.json                          # 当前指针、输入集合、刷新原因及代次
      revisions/<knowledge-revision-id>/
        manifest.json                    # 实际依据、输出、基线
        wiki/                            # 编译器原目录结构，可独立读取
    intents/                             # 持久任务的空间预留，细节归恢复决策
    proposals/<proposal-id>/              # 持久的人工差异/冲突候选及其引用
    staging/<operation-id>/               # 临时工作副本，不作为历史证据
    journal/                             # 复用现有事务日志
```

`revisions/.../wiki` 是已发布快照；在 staging 的工作副本运行原编译器，完成后发布快照及 head。首版可使用真实文件副本，不先造增量版本存储；原件和图片通过受管引用共享，避免每次知识快照重复大二进制。仅在确认所有写入都使用替换而非原位覆盖后，才考虑现有 hardlink 优化。当前目录不用符号链接。

这比“一个巨大 manifest 加原地覆写全局 Wiki”多了修订目录，但能够保留旧正文和生成基线。仅给全局 Wiki 加版本字段无法满足相反版本共存；额外引入 SQLite 也不能替代不可变正文与文件事务，当前没有必要。

## 5. 三个小例子

### 同字节、不同来源

来源 A 与 B 具有不同 `source_id`，各有自己的 SourceRevision/ImportUnit；二者可引用同一内容 blob。A 的成功记录不能直接让 B 的接入被 hash skip。重复执行 A 的同一导入意图则复用既有提交，不重复发布。重复来源关系不是字节存储去重关系。

### 两版工作簿、一个失败 sheet

V9.3 已发布 S1/S2；接入 V9.4，S1 成功、S2 失败。V9.4 head 只把 S1 的新修订纳入有效输入，S2 的失败另存；文档列表可显示 S2 的 V9.3 成功结果，但 V9.4 问答不能读取它并称为新版依据。V9.3 的知识视图保持可读。

若是同一适用版本的资料修订更新，S2 失败时保持该单元在该视图的旧成功引用，并标记本次更新失败；不得偷偷把它的来源修订改成新原件。确认空 sheet 则提交明确的空处理结果、撤去当前贡献并标记受影响页面，不能等同于失败或仅图未提取。

### 旧 Wiki 含未分版本知识

保留现有 Wiki，以 `legacy` 视图读取；从实际现存原文/处理结果建立已知基线，不声称能恢复早期引用当时未记录的历史版本。旧 registry 中因 hash 合并已丢失的来源身份，不能凭空补造。

新版本发布到独立视图，不能给旧混合概念页贴 V9.4 标签，也不能把 legacy 默认复制为新版编译上下文。升级可做不调用模型的记录映射；真正拆分旧混合知识须显式重新处理/编译。无新视图时旧查询继续可用；有明确新版本请求时 legacy 只能作为单独注明的历史参考。

## 6. 共用 scope、页面依赖与人工保护

采用一个范围解析入口，返回编译/只读两种小对象：

```text
CompilationScope = real_kb_root, view_id, staging_wiki_root,
                   base_knowledge_revision_id, expected_view_generation,
                   allowed_unit_revision_ids, generation_baselines

ReadScope = view_id, knowledge_revision_id, wiki_root,
            allowed_source_revisions, page_validity
```

这些是职责草图，不是新工作流框架。真实 KB 决定配置、凭据和锁；视图决定正文上下文及输出目录。编译入口、问答/chat/skill、原文读取、lint、页面编辑和 backlink 使用同一范围。相对 Wiki 链接只在所在视图解析；明确跨视图链接必须携带视图身份，不能靠同名文件回退。

现有 compiler 内部大量 helper 已传 `wiki_dir`，优先复用；只补真正硬编码的入口和外部传入摘要/原文的归属校验。只读工具创建时即限定范围，并固定本次知识修订，防止一次回答读到两代混合正文。查询结束前若有效性代次改变，应报告依据已变更，不能继续宣称为当前已验证结果。

知识页依赖不能仅记录“这次导入的一个 unit”：现有编译器会合并已有概念正文。新页至少保留被使用旧页的依据集合及本次输入；无法精确分辨时采用保守依赖集合，允许多标待刷新，不虚构逐句贡献。上下文中待刷新页面不能作为当前已验证依据。普通编译碰巧更新同名页，不等于已消除它的全部待刷新原因；只有核验实际输入与刷新基线后才能清标记。

按已接受 ADR 0008：生成时保存正文基线；人工修改或未知基线时保留原页、保存建议差异，明确接受后才更新。候选正文、差异、基线及资产引用在释放 worker/锁前提交到持久 proposals；现有 `run_add_mutation` 会清理临时 staging，不能只留下临时路径供用户下次确认。用户接受时仍检查最新基线。保存 hash CAS、防止迟到任务、人工基线检测是三个不同检查。不能因为持有 KB 锁就默认没有人工修改。

人工编辑也生成新的知识修订，保留原模型生成基线和编辑信息；不是直接修改历史快照。legacy 未知基线不得自动填“当前正文即上次模型生成结果”来绕过保护。受保护页冲突阻止该单元本次知识发布，其他已成功 sheet 不回滚。

## 7. 提交与引用保留的必要边界

本票只固定一致性要求，具体 intent 状态机和故障恢复属于后续恢复契约。

1. 接入提交：来源修订、冻结原件引用、附件发现意图一起保存；此后正文失败不撤销接入。
2. 单元发布：新知识快照、head、该单元在视图中的发布状态、来源依赖、刷新原因和业务检查点一起提交。先校验目标来源/单元代次与视图基线，全部路径必须加入现有 mutation。
3. 多个有效单元基于同一旧视图并发生成时，后完成者不能仅切指针而覆盖先发布结果。基线不匹配将需保留的候选提交为持久 proposal 并报告冲突，临时 staging 随后可清理；不得自动合并未知模型输出或覆盖人工页。现有串行 KB 执行优先保留。
4. 迟到旧任务可以保留历史处理结果；是否具有可独立阅读的完整历史知识快照取决于其有效基线，不能保存半成品后称成功。它不改变目标版本、当前指针或默认选择。
5. 失败诊断在该单元事务回滚后另行保存；一般可发布的提取警告不自动升级为失败。`needs_refresh` 原因与触发它的有效来源变化一同提交，刷新失败不清原因。
6. 删除/清理检查所有活跃、历史、待确认建议和待执行意图引用，不仅 HashRegistry。删除父来源只解除附件 active 关联；附件与待执行任务保留。未引用历史仍遵守已接受的显式清理规则。

新程序所有写入口检查 schema/capability。尚不能保证已经发行的旧二进制会识别新标记；交付契约须明确最低可写版本和混用限制，不承诺旧版继续安全写入新结构。新目录与 legacy 扫描隔离也不能代替这一检查。

## 8. 最小函数接缝与简单验收

| 接缝 | 修改/新增边界 |
| --- | --- |
| 读取来源/修订 | 新增共同记录存取和 legacy 映射；HashRegistry 不双写成第二权威 |
| `prepare_compile_view()` | 解析范围、准备工作副本与生成基线；不调用新摘要算法 |
| `compile_short_doc()` / `compile_long_doc()` | 接收 scope，复用已有 wiki_dir helper 与原全文/完整树编译 |
| `resolve_query_views()` / 共同范围解析 | 查询、读取、lint、编辑、skill 使用一致目录和来源范围 |
| `publish_unit_revision()` | 形成显式路径计划，复用 mutation 和代次检查；不把调用旧事务函数等同于新目录已受保护 |
| `mark_affected_views_needs_refresh()` | 根据保存的依赖保守标记；不调用模型，不重写历史正文 |
| `list_artifact_references()` | 删除、上传清理与索引清理共用，涵盖历史和意图 |

测试仍采用小固定输入、一次动作、少量断言：

- 两个来源共用一份小字节文件，来源身份仍为两个。
- 同产品同适用版本的两个资料系列解析到同一个 view，来源和修订仍各自独立。
- 两个视图包含同名且相反结论的概念页，指定一版的工具读不到另一版。
- 单元更新失败，成功修订指针不变，失败记录保留。
- 旧页未知生成基线，候选保存为持久 proposal，清理 staging 后仍可读取，当前正文未被覆盖。
- 发布前视图代次变化，新结果不得覆盖当前指针。
- 来源撤回，共享页带待刷新原因且历史仍能回读；测试不调用模型。
- 历史知识/持久意图仍引用的资产，清理计划不得删除。
- legacy 记录映射不调用转换器或模型，不改变旧正文。
