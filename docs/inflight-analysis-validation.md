# 在途分析与单次记账验收（#42）

2026-09-13 补齐受控 HTTP 服务与真实进程故障注入。新增验收不调用付费模型。

## 结果与修复

`tests/test_shared_flight_acceptance.py` 的 7 个场景通过，覆盖以下组合：

| 场景 | 可观察结果 |
|---|---|
| 三个消费者，一个等待者取消 | 只有一个 HTTP 分析请求；其余两个消费者得到同一结果，分别绑定自身来源；退出者不绑定 |
| 一个等待者等待超时 | 返回 `analysis_wait_timeout`；执行者和另一等待者仍完成 |
| 一个等待者文档时间耗尽 | 返回 `time_budget_exhausted`；不影响其他消费者 |
| 一个等待者 token 预算耗尽 | 请求在派发前被拒绝；等待退出，其他消费者仍完成 |
| HTTP 已到达后杀死执行者进程 | 先回收执行进程，再显式继续；接管成功发布；释放旧 HTTP 响应不改变已发布文件；完成复导不再请求 |
| 120 个重复原文块，提供方返回用量 | 每个实际 HTTP 请求具有唯一计量 ID；总账只计一次；120 个原文位置全部绑定；保留等待、复用与绑定事件 |
| 同上，但提供方省略用量 | 未知用量保留，按预留值占用预算，不把 SDK 生成的零视为免费 |

故障注入暴露两个缺陷，已修复：

1. 执行者被杀死时，尚未生成来源终态收据，实际已发送的请求会从来源累计账本消失。现在在传输前写入请求日志，并在用量结算时更新；读取来源历史时，只补入尚未出现在终态收据中的请求 ID。嵌套文档共享上层预算，避免重复登记。
2. 当前固定版本 LiteLLM 会把 OpenAI 格式的缺失用量正规化为 `0/0`。现在在同步和异步调用中观察原始响应是否明确提供输入、输出计数，缺失或部分计数保留为未知；明确返回的 `0/0` 仍有效。观察器只保留判断状态，不保存响应正文或认证信息，并继续调用已有 logger 回调。

`tests/test_provider_usage.py` 的 8 个真实本地 HTTP/SDK 测试分别覆盖同步、异步以及空值、空对象、部分计数、明确零值。来源请求日志使用现有原子写入接口；没有增加 Wiki 发布入口。

## 验证与边界

- 完整回归：**1,992 passed、1 skipped，488.23 秒**。另有 3 个 LiteLLM 异步日志清理警告，无测试失败。
- 修改文件的 ruff、格式检查通过；mypy 检查 291 个应用模块通过。
- 完整回归使用离屏 Qt 和可导入的文件入口，保持一个 QApplication。此前标准输入入口导致 52 个 multiprocessing spawn 失败；未把这次错误运行计为产品回归通过。更早缺少 QApplication 的运行也保留为失败记录。
- 新增进程验收实际运行于本轮 Linux 环境。没有声称重做 Windows 硬件或 OCR 平台验收。
- 被杀死进程的服务端最终费用无法从客户端恢复时，仍是未知；“没有重复发布”不代表服务端没有处理旧请求。客户端进程仍存活的实验外层观察器可以继续收取晚到用量，但不能反向把历史未知收据补零。
- 这是 #42 所列并发组合的离线验收结果；不能代替 #13/#45 的真实语义、引用和成本验收。真实小样本结果见 [小文档校准](small-document-calibration.md)。
